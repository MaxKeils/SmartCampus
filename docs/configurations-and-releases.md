# Регламент конфигураций и релизов SmartCampus

## Конфигурации

| Где | Что хранится |
|---|---|
| Git | Gradle Wrapper с контрольной суммой, фиксированные версии зависимостей, декларации Android-модуля, workflow, синтетические данные |
| Рабочая станция | `local.properties` с путём к Android SDK или переменная `ANDROID_HOME`, путь к JDK 25 |
| Репозиторий GitHub | Несекретные переменные CI и параметры защищённых веток |
| Среда выпуска | Ключ подписи и пароли в согласованном защищённом хранилище. При появлении CI-подписи передавайте значения только через секреты среды выпуска |

Pull request собирает отладочный APK на учебных данных. У workflow минимальный доступ на чтение репозитория. Он не использует ключ выпуска. Реальные данные ВятГУ, токены, пароли, файлы подписи и локальные пути разработчиков не коммитятся.

При изменении конфигурации укажите, какое окружение затронуто и какие действия нужны при обновлении. Изменения пути к SDK остаются локальными. Если в будущем появится подключение к вузовскому API, согласуйте демонстрационный и пилотный контуры до добавления конфигурации для подключения.

## Подготовка и выпуск

1. Ответственный создаёт `release/X.Y.Z` от зелёного коммита `develop` и фиксирует список задач по версии.
2. Обновляет `versionName` и увеличивает `versionCode` в `app/build.gradle`. Кандидат может иметь суффикс `-rc.1`. Для окончательного выпуска задаётся стабильная версия X.Y.Z и следующий свободный `versionCode`.
3. Открывает PR в `main`. Прикладывает список изменений, проверки приёмки и ссылку на CI. Блокирующие ошибки устраняются в релизной ветке. GitHub Actions публикует APK для демонстрации и результаты тестов как артефакты проверки.
4. После одобрения и зелёного CI сливает PR. Создаёт тег `vX.Y.Z` на принятом коммите `main`. Запись GitHub Release содержит изменения, ограничения, ссылку на сборку и контрольные суммы прикладываемых файлов.
5. Для пилотной или публичной дистрибуции используется отдельно согласованная release-сборка с ключом проекта. Отладочный APK из CI используется для лабораторной демонстрации.
6. Возвращает релизные исправления в `develop` через PR и закрывает карточки после проверки принятого результата.

## Восстановление

Остановите распространение неисправной версии, зафиксируйте проблему в Jira и определите последний проверенный тег. При разрешённом откате используйте его проверенный артефакт. При запрете понижения Android-версии соберите исправление с увеличенным `versionCode`. Исходники исправляются веткой `hotfix/*` и проходят CI. Опубликованные теги сохраняют связь с первоначальными артефактами.
