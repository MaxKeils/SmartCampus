# Регламент Git Flow SmartCampus

| Ветка | Назначение | Начало | Pull request |
|---|---|---|---|
| `main` | Принятые версии | Постоянная | Из `release/*` или `hotfix/*` |
| `develop` | Интеграция следующей версии | Постоянная | Из `feature/*`, `release/*` или `hotfix/*` |
| `feature/SCAMP-номер-краткое-имя` | Работа по одной карточке Jira | Актуальный `develop` | В `develop` |
| `release/X.Y.Z` | Стабилизация версии | Проверенный `develop` | В `main`, затем синхронизация `develop` |
| `hotfix/X.Y.Z` | Срочное исправление выпущенной версии | `main` | В `main` и `develop`, при необходимости в открытый `release/*` |

## Работа над карточкой

1. Исполнитель берёт карточку в Jira и создаёт ветку от актуальной базы.

   ```sh
   git fetch origin
   git switch -c feature/SCAMP-9-offline-schedule origin/develop
   ```

2. В коммите укажите действие и ключ задачи. Например, `SCAMP-9 Проверить сохранённое расписание при сбое источника`.
3. Откройте pull request и укажите ключ Jira, результат, способ проверки и влияние на конфигурации. Переведите карточку в Review после готовности к просмотру.
4. Ревьюер сверяет критерии приёмки и проверку `Android tests and build`. При изменениях обновите ветку, разрешите конфликты и заново дождитесь CI. Автор обращает внимание ревьюера на изменения после предыдущего одобрения.
5. Слейте feature-ветку через pull request. Обычный режим для коротких feature-веток — squash merge. Для переноса принятой истории `release/*` и `hotfix/*` используйте merge commit, чтобы сохранить результаты стабилизации при синхронизации долгоживущих веток.
6. Переведите карточку в Done после слияния и выполнения её критериев. После завершения работы короткоживущую ветку можно удалить.

## Защищённые ветки

Для `main` и `develop` требуется pull request, успешная проверка `Android tests and build` на актуальном состоянии базы и разрешение обсуждений. Принятие изменений требует одного одобрения участника команды. Удаление ветки и force push запрещены. Релизные ветки используются для исправлений и подготовки материалов выпуска через pull request. Параметры можно восстановить в GitHub через импорт [правил веток](../.github/rulesets/git-flow.json).

Ответственный за релиз следит за версией, артефактами и синхронизацией `develop`. Подробный порядок выпуска описан в [регламенте конфигураций и релизов](configurations-and-releases.md).
